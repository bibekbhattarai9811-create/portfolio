Overview

The problem

Unplanned equipment failure is expensive: lost production, emergency repairs and safety risk. Predictive maintenance asks two questions of sensor data: how much useful life does this machine have left, and how likely is it to fail soon?

I wanted a project that showed the full loop rather than a notebook: data with a real physical story, evaluation that can't cheat, a served model, and an interface a non-technical person can read.

Data

Simulating a fleet

Public datasets such as NASA's C-MAPSS are awkward to fetch reliably or licensed for competition use only, so I generated run-to-failure telemetry for 100 pumps, encoding the same physics those datasets rely on.

Each pump's hidden wear drifts upward as a Wiener process (a random walk with drift), so failure timing varies unit to unit like real equipment. Five sensors respond to that wear with different sensitivities and noise: vibration, temperature and pressure react directly, lubricant quality degrades alongside it, and RPM stays near its setpoint. A per-unit load factor between 0.8 and 1.2 keeps the fleet from being identical.

Approach

Modeling

  1. Feature engineering

    Raw readings plus 5-cycle rolling means and standard deviations, the operating cycle and each unit's load factor.

  2. Remaining useful life

    A gradient-boosted regressor predicts cycles remaining, capped at 125, the standard piecewise-linear labeling, because early-life wear isn't visible in sensors.

  3. Failure risk

    A gradient-boosted classifier predicts the probability of failure within the next 30 cycles.

  4. Serving

    A FastAPI backend loads both models at startup and serves fleet status, per-unit history, live what-if predictions and evaluation metrics to a Next.js dashboard.

Decisions

Key decisions

Split by pump, not by row

Rolling features mean neighbouring rows share information. Splitting randomly by row would let a test pump's future leak into training, so whole pumps go to either train or test (GroupShuffleSplit).

A realistic snapshot of the fleet

Every simulated pump runs to failure, so its last row is always the failure point. Showing that as current status would make the whole fleet look critical, so each pump gets a fixed "observed as of" cycle somewhere in its life.

Make the model legible

A what-if simulator lets anyone drag sensor sliders and watch predicted life and risk update live, which explains the model better than a metrics table.

Show what the model knew

Unit charts draw a "today" marker separating what the model had seen from the hindsight-only part of the run.
